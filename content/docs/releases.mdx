`+` is new, `-` is gone, `!` is something you have to know about before you upgrade.

## 3.2.0

Everything that could fail now answers the same way, whichever door you came through.

```diff
+ Flush, Compact and Release name the reason they failed
+ Store:Resettle is part of the api, and handles its key like every other method
+ Ledger.HistoryEntry is exported, so a Store:History result can be typed

! Store:Resettle hands back a Future now, so it needs :Wait()
! Tx answers Invalid for a leg field it cannot store, it used to throw
! A Once name that is empty or not a string answers Invalid, it used to throw
```

### Upgrading

`Flush`, `Compact` and `Release` return a reason next to the boolean. The boolean means what it
always meant, so you can ignore the reason and change nothing. See
[Session](/docs/reference/session#flush).

`Resettle` needs a change if you were calling it. It was reachable before but never declared, and it
took a key string through without checking it. It is on `Store` now. It resolves the key the way
`Peek` and `Edit` do, so a bad one throws where you wrote it, and it answers
`Future<boolean, Reason?>`. Add `:Wait()`. `true` means nothing is left unfinished on the key. `Busy`
means a transaction leg is still waiting on a decision, so try again later. See
[Resettle](/docs/reference/store#resettle).

`Tx` used to throw when a leg's `Fields` held something a datastore can't take. It answers
[`Invalid`](/docs/concepts/reasons) now, the same as `Edit` already did for the same content. Leg
fields are usually calculated, so `Fields = { Amount = Price * Count }` can produce a NaN, and that
used to crash the caller. If you wrapped `Tx` in a `pcall` for this, read the reason instead. The
shape of a leg still throws, so a bad key, a duplicate key or a `Once` on a leg is unchanged.

`Once` moved for the same reason. You pass it in `Fields`, and a name almost always comes from
outside your game. A receipt id or an order id that arrives as `nil` used to crash `Apply`, `Commit`
and `Edit`. All four surfaces answer `Invalid` now, the same as `CommitOp` already did. See
[Once](/docs/concepts/once#rules).

`Ledger.HistoryEntry` is exported. `Store:History` always returned them and there was no way to name
the type. Nothing changes if you were not asking for one.

### Check your own reducers

The entity store example in these docs was wrong until now. It kept members in a table keyed by
UserId:

```luau
State.Members[Op.UserId] = true             -- wrong
State.Members[tostring(Op.UserId)] = true   -- right
```

A table with only number keys is an array, and a UserId is a huge number, so that table is an array
with millions of gaps. A datastore cannot store it. Each op passes on its own, so your writes keep
working. The key then fails to compact and the log grows forever.

The same example used `#State.Members` for a member cap. `#` gives `0` on a dictionary, so the cap
never applied.

If a table in your reducer has ids for keys, make them strings. See
[What you can store](/docs/concepts/the-fold#what-you-can-store).

## 3.1.2

Op ids got shorter, and there is a way to read the record on a key rather than the state it folds to.

```diff
+ Buffers can live in state and in ops
+ Store:Inspect, the record on a key rather than the state it folds to
+ Op ids named after the server and counted, half the length of the old ones
```

### Upgrading

A buffer in state is copied rather than shared, so one session writing into one can't reach another.
Freezing can't cover it though, since Luau has no way to freeze a buffer, so build a new one rather
than writing into the one your reducer was handed. See
[Writing a reducer](/docs/concepts/reducer#it-has-to-not-mutate).

Op ids changed shape and nothing has to be done about it. An id is opaque, compared only for equality,
so ids written by older builds keep working next to the new ones and there is no migration. If you
were reading op ids expecting a GUID, they now look like `3c404902bf6a4a4e:41`.

## 3.1.1

Erasing a key could destroy money that was still on its way to it, and a failed load had one
answer for every reason it might have failed.

```diff
+ OnLoadFailed, so a failed load can teleport or retry instead of always kicking
+ Erase leaves a tombstone, so money still on its way in goes back to whoever sent it
+ Making ledger smarter, being able to spot future failures quicker

- A transfer landing mid erase being destroyed with the sender already settled

! Erase leaves the key in place as a tombstone for 8 days, it used to delete it
! Sending to a key that was erased answers Refused rather than going through
```

### Upgrading

`Erase` is the one you can see from outside. It leaves a tombstone rather than deleting the key, so a
transfer already on its way in gets refused and refunded. Reads of an erased key are unchanged, they
still come back as a fresh profile, and any ordinary write clears the tombstone. If you have tooling
that checks the key is really gone, call `Erase` a second time after the 8 days and it removes it.
See [Erase](/docs/guides/recovery#erase).

`OnLoadFailed` is opt in and the default is the kick you already had, so nothing changes unless you
pass it. Pass it if you deploy while people are playing, since `Behind` wants a teleport and a rejoin
can't fix it. See [Ledger.New](/docs/reference/ledger#onloadfailed).

## 3.1.0

Every method that could fail now says why. Before this, a read that failed handed you back nothing
at all, which arrived in your variable as `nil` and looked exactly like a player with no data.

```diff
+ Every read says why it failed, the same way every write already did
+ Behind, a ninth reason, for a record a newer build wrote
+ Erase, RecoverTransfers and ClearDelivered say whether they ran

- Reads that failed by handing back nothing, with no way to ask what went wrong
- A datastore blip and a record this server must not touch looking the same
- A failed DidApply reading as never granted, so a support tool pays twice

! Reads answer (value?, Reason?), and nil always means the read failed
! Store:DidApply can be nil, so compare it against true rather than truthiness
! Reset on a record from a newer build says Behind, it used to say Refused
! Writes dropped by the shutdown say Closed, they used to say Unresolved
```

### Upgrading

Most code keeps working. A missing first return was already `nil`, so `if Ok then` and
`if State == nil then` behaved the same before and after. What changes is that you can now tell the
failures apart, and strict mode will point at the call sites worth revisiting.

The one that can cost you money is `DidApply`:

```luau
-- before, and now wrong: a failed read reads as never granted, so you grant again
if Store:DidApply(UserId, Name):Wait() then

-- now
if Store:DidApply(UserId, Name):Wait() == true then
```

And if you match on reasons to decide whether to retry, add `Behind` to the "don't bother" side. It
means this server is running an older build than the one that wrote the record, so retrying can't
help and writing a fresh profile over the top would destroy real data. See
[Reasons](/docs/concepts/reasons).

## 3.0.1

```diff
+ Edit and Reset prove their answer against a pending transaction instead of guessing
+ Markers on keys holding a delimiter byte reap like any other
+ OnceAt joins Id and Kind as reserved, overwritten with a warning
+ Warnings rewritten in plain speech, what happened and what to do about it

- A marker naming a key with \0 or \1 in it could never be collected by anyone
- A forged OnceAt could wipe the applied id set and pay a delivered transfer twice
- Edit answering true for a verdict a pending leg was about to overturn
- Reserve reporting money set aside without saying on what terms
- Loading and Leaving as two maps that could disagree about one player

! Edit and Reset answer Unresolved when a stuck leg could still flip the verdict
! OnceAt in Fields is overwritten now, CommitOp still honours an op's own stamp
! Mid deploy, a transaction retried across versions can answer Spent once, nothing applies
```
